# PRD — ИИ-ассистент для чата на ekt.kz

Первичный источник требований — [итоговое Word ТЗ HackAlem AI](<assets/HackAlem AI_ ИИ-ассистент для чата на сайте ekt.kz.docx>). Этот PRD и [Use Cases](use-cases.md) переводят его в проверяемые сценарии; иерархия документов закреплена в [source of truth.md](<source of truth.md>).

## Главная задача и ценность продукта

Создать в одном окне чата на ekt.kz ИИ-ассистента, который помогает клиенту выбрать электротехнический товар по данным каталога: сообщает характеристики, сертификаты и наличие, предлагает обоснованные аналоги, объясняет условия покупки и **только после явного подтверждения** добавляет выбранное количество в корзину. Это задача раздела 4 [итогового Word ТЗ HackAlem AI](<assets/HackAlem AI_ ИИ-ассистент для чата на сайте ekt.kz.docx>), а не описание уже работающего приложения.

Ценность из раздела 2 ТЗ: сократить время решения о покупке и число типовых обращений к менеджеру, уменьшить уход покупателей на этапе консультации. Первый приоритет — доказать эту ценность хотя бы на одном полном пути **UC-01: вопрос клиента → факты из каталога → проверяемый ответ о товаре и наличии**. Остальные обязательные возможности расширяют этот путь после его проверки.

## Пользователь и ключевой сценарий

Пользователь — частный покупатель или закупщик компании, выбирающий электротехническую продукцию на ekt.kz (раздел 3 ТЗ).

**Ключевой сценарий продукта:** клиент открывает чат на сайте → спрашивает о товаре, наличии, аналоге или условиях покупки → получает ответ из подтверждённых источников → при готовности выбирает товар и количество → явно подтверждает добавление → видит обновлённую корзину и прямую ссылку для оформления. Это целевой путь всего продукта. Первая реализуемая и проверяемая часть — UC-01; ветви аналога, условий и корзины представлены отдельными UC-02…05.

## UC-01 — Информация о товаре и наличии: первый сквозной результат

**Основание:** разделы 3–6 и пункт 1 раздела 7 Word ТЗ. UC-01 несёт контекст главной задачи и задаёт общую цепочку «ввод → получение данных → ответ», которую затем используют UC-02…05.

**Вход:** свободный вопрос клиента о существующем товаре, его артикуле или характеристиках; контекст текущей сессии. По полному ТЗ входом также служат фото и файлы Excel, Word, PDF, JPEG (например, спецификация или накладная): из них нужно извлекать товар или свойства. Первый сквозной прогон допускает текст и один артикул; это не закрывает требование к вложениям.

**Данные:** каталог и остатки ekt.kz или явно обозначенная репрезентативная анонимизированная/синтетическая выборка. По разделу 6 ТЗ нужны артикул, название, категория, ключевые характеристики, сертификат/ссылка при наличии, цена, остаток по складам и статус наличия. В [проверенном API](../../contracts/ekt-catalog-api.md) список содержит `id`, `article`, `name`, `price`; детали по числовому `id` содержат `description`, `properties`, `quantity`, `stores`. Поиск по артикулу, отдельное поле сертификата, валюта цены и свежесть остатков не подтверждены. [Pydantic-контракты](../../backend/app/schemas/ekt_catalog.py) и [OpenAPI-схема](../../contracts/ekt-catalog.openapi.json) фиксируют наблюдаемую структуру, а не обещают недостающие поля.

**Обработка и выход:** чат передаёт запрос в наш API; backend сопоставляет артикул с `id`, получает детальную карточку, формирует ответ из подтверждённых полей и показывает название, значимые характеристики, наличие и источник/время получения. Сертификат или ссылку предоставляет только при наличии в подтверждённом источнике. Если источник не содержит нужное поле, ассистент обозначает ограничение. Ожидаемая задержка по разделу 5 ТЗ — единицы секунд при доступных источниках; численный порог не задан.

**Приёмка UC-01:** запрос контрольного артикула в браузере приводит к ответу, где артикул, технические характеристики и остаток совпадают с актуальным источником; сертификат выдаётся, если он есть в базе. API-проверка сверяет значения с источником, браузерная — доступность ответа клиенту. Неизвестный артикул, отсутствие сертификата и недоступность/устаревание источника не создают вымышленных сведений о цене, наличии или свойствах. Для снимка каталога видны источник и время получения. Прогон на демонстрационных данных отмечается как демонстрационный; готовность интеграции подтверждает только живой прогон с фактическим источником. Пока источник сертификатов не выяснен, условие приёмки по сертификату нельзя считать подтверждённым.

## Остальные обязательные Use Cases — после UC-01

| UC и пункт раздела 7 Word ТЗ | Вход → ожидаемый результат | Проверяемая приёмка |
| --- | --- | --- |
| **UC-02 — аналоги, п. 2** | Запрос позиции с нулевым остатком → минимум один доступный релевантный аналог из каталога с кратким объяснением совпадений и отличий. | Аналог существует, имеет подтверждённое наличие и подходит по значимым характеристикам. Если аналога нет, ассистент сообщает об этом. |
| **UC-03 — условия покупки, п. 3** | Вопрос об оплате, доставке или минимальной партии → содержательный ответ из утверждённого источника. | Проверены все три темы; неподтверждённые условия не выдумываются. Источник условий ещё нужен от партнёра. |
| **UC-04 — подтверждаемое добавление, п. 4** | Выбранные артикул и количество, затем отдельное явное согласие → изменение только корзины текущего клиента с учётом остатка. | До согласия корзина не меняется; после согласия артикул и количество верны, количество не превышает остаток. Отмена, двусмысленный ответ или изменение выбора требуют нового согласия. Контракт корзины ekt.kz ещё нужен. |
| **UC-05 — ссылка на корзину, п. 5** | Успешное добавление по UC-04 → прямая ссылка на корзину/оформление. | Ссылка открывает актуальную корзину с добавленной позицией. Локальная демонстрационная корзина не подтверждает выполнение UC-05 на ekt.kz. |

UC-02 использует товарные факты UC-01; UC-03 требует отдельного источника условий; UC-04 опирается на остаток и защищённую сессию; UC-05 возможен только после успешного UC-04. Эти зависимости не меняют приоритет: сначала завершить сквозной UC-01.

## Ограничения и границы прототипа

- Нельзя менять корзину или оформлять заказ без явного согласия, сообщать недостоверную цену/наличие, запрашивать или хранить платёжные данные (раздел 9 ТЗ).
- Нужны приватность данных клиента, защита от изменения чужой корзины, объяснимость аналогов, совместимость с сайтом и работа на компьютере и телефоне. Ответ модели и содержимое вложения сами по себе не являются согласием.
- Учётные данные API не помещаются в код, документацию или логи. Допустимость передачи клиентских вложений стороннему AI-сервису и правила встраивания требуют согласования.
- Анонимизированная или синтетическая выборка допустима для демонстрации прототипа с явной маркировкой. Она не доказывает актуальность данных ekt.kz. Локальная корзина не доказывает интеграцию с корзиной сайта.
- Функции раздела 8 ТЗ — казахский язык, сопутствующие товары, история для авторизованных клиентов и передача сложных вопросов менеджеру — опциональны после обязательных сценариев.

## Готовность и открытые зависимости

UC-01 считается выполненным только после сквозного пользовательского прогона и проверки его критериев выше. Затем отдельно проверяются UC-02…05. Полный прототип по разделу 7 ТЗ требует всех пяти пунктов, включая обработку заявленных входов из раздела 5. Для этого ещё нужны подтверждение поиска по артикулу и сертификатов, источник условий покупки, контракт и доступ к корзине, правила встраивания и обработки вложений. Результаты и ограничения прогона фиксируются в README и [ROADMAP](../../ROADMAP.md).
