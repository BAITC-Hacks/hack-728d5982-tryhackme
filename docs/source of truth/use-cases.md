# Use Cases — кейс ekt.kz

[PRD](PRD.md) задаёт обязательное поведение; источник — [итоговое Word ТЗ HackAlem AI](<assets/HackAlem AI_ ИИ-ассистент для чата на сайте ekt.kz.docx>). Здесь описаны пользовательские прогоны и наблюдаемые результаты. **UC-01 — первый сквозной сценарий и текущий приоритет.** UC-02…05 соответствуют пунктам 2–5 раздела 7 ТЗ и расширяют его после проверки.

## Главная задача и ключевой сценарий

Клиенту ekt.kz, частному покупателю или закупщику компании, нужен быстрый достоверный ответ в одном чате, чтобы решить, что покупать, без типового обращения к менеджеру. Ассистент консультирует по каталогу и остаткам, при необходимости предлагает аналог или объясняет условия покупки, затем **только после явного согласия** меняет корзину и даёт ссылку на неё. Это полная продуктовая цепочка из разделов 2–5 Word ТЗ; первый доказуемый участок цепочки — ответ по конкретному товару в UC-01.

## UC-01 — информация о товаре и наличии (Must have 1)

| Элемент | Содержание |
| --- | --- |
| Пользователь | Клиент ekt.kz на компьютере или телефоне. |
| Запуск | Клиент в чате спрашивает о товаре по артикулу или характеристикам. Для первого прогона — текстовый артикул; полный вход ТЗ также включает фото, Excel, Word, PDF и JPEG. |
| Контекст и данные | Текущая сессия; каталог/остатки ekt.kz либо явно обозначенная демонстрационная выборка. Нужны артикул, название, характеристики, сертификат при наличии, цена и остатки по складам. |
| Действие системы | UI → наш API → сопоставление артикула с числовым `id` → `GET /api/products/detail?id=…` по [контракту](../ekt-catalog-api.md) → проверка и нормализация фактов → ответ в чате. Список `/api/products` не содержит остатков и свойств; поиск по артикулу в предоставленном API не подтверждён. |
| Видимый результат | Название и артикул, существенные технические характеристики, наличие с указанием источника и времени получения, ссылка/файл сертификата только при подтверждённом наличии. Неизвестные поля обозначаются как неизвестные. |
| Критерий | Для контрольного артикула ответ совпадает с фактической детальной карточкой по характеристикам и остатку; сертификат показан, если есть в базе. Браузерный прогон подтверждает, что клиент видит результат; API-проверка сверяет значения и ошибку источника. |
| Исключения | Неизвестный артикул, недоступный/устаревший источник и отсутствие сертификата не приводят к выдуманной цене, наличию, свойствам или сертификату. При снимке данных отмечены источник и время получения. |

Проверочные входы: существующий артикул с известными свойствами и остатком; отсутствующий артикул; позиция с нулевым остатком; товар с сертификатом, если такой пример и источник доступны; недоступный источник. Известный `id=515291` подтверждает форму детального ответа, но **не заменяет** проверку поиска по пользовательскому артикулу и сертификата. Цель ответа — единицы секунд при доступном источнике; точный порог ТЗ не задаёт.

**Состояние:** Pydantic-модели и OpenAPI-схема отражают наблюдаемое API; пользовательский путь «чат → фактическое чтение → ответ» ещё не проверен. Источник сертификатов, полнота каталога и свежесть остатков остаются открытыми. До их выяснения UC-01 нельзя отметить как выполненный.

## UC-02 — релевантный аналог (Must have 2)

**Вход:** запрос товара с нулевым остатком. **Результат:** существующий доступный аналог из каталога с кратким объяснением общих значимых характеристик и отличий. **Приёмка:** артикул, характеристики и остаток аналога проверяются по тому же источнику, что в UC-01; при отсутствии подходящего аналога ассистент сообщает об этом. `offers` из API не считать аналогами без подтверждения их структуры.

## UC-03 — условия покупки (Must have 3)

**Вход:** вопрос об оплате, доставке или минимальной партии. **Результат:** содержательный ответ из утверждённого источника. **Приёмка:** отдельно проверены все три темы; если источник не предоставлен, ассистент прямо говорит, что условия не подтверждены. Каталог товаров не содержит подтверждённого контракта этих условий.

## UC-04 — добавление после явного согласия (Must have 4)

**Вход:** выбранные артикул и количество, затем отдельное явное «да, добавь». **Результат:** только корзина текущего клиента меняется после повторной проверки остатка. **Приёмка:** состояние корзины до предложения и до согласия одинаково; после согласия добавлены правильные артикул и количество, не превышающее остаток. Отмена, двусмысленный ответ, смена позиции/количества и запрос сверх остатка не выполняют действие. Нужны контракт корзины и способ привязки сессии ekt.kz.

## UC-05 — прямая ссылка на актуальную корзину (Must have 5)

**Вход:** успешное добавление в UC-04. **Результат:** прямая ссылка на корзину/оформление. **Приёмка:** ссылка открывает актуальную корзину с только что добавленным товаром и количеством. Ссылка на локальную демонстрационную корзину не подтверждает работу на ekt.kz.

## Порядок и общие ограничения

`UC-01 → UC-02/UC-03 → UC-04 → UC-05` — порядок расширения работающего пути, а не заявление о готовности. Отдельный источник условий для UC-03 можно согласовывать параллельно. Поддержка вложений, мобильного интерфейса, приватности, запрет обработки платёжных данных и защита корзины относятся к полному ТЗ и проверяются по мере включения соответствующего входа/действия. Полный статус указан в [ROADMAP](../../ROADMAP.md); демонстрация на синтетических данных всегда помечается отдельно от живого прогона.
