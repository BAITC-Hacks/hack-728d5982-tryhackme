# Каталог ekt.kz: наблюдаемый контракт и пробелы для UC-01…05

Основание: [ТЗ](source%20of%20truth/PRD.md), предоставленный партнёром документ `docs/source of truth/assets/ИИ-ассистент для чата на сайте ekt.kz ДАННЫЕ.docx` и **живые запросы 23.09.2026, 08:46 UTC**. Это снимок наблюдаемого поведения, а не гарантия неизменности API. Учётные данные здесь и в схемах отсутствуют.

Исходник типов — [`EktProductPage`, `EktDetailProduct`, `EktError`, `CatalogProductFacts`](../backend/app/schemas/ekt_catalog.py). [OpenAPI 3.1](ekt-catalog.openapi.json) генерируется из этих Pydantic-моделей; команды из `backend/`:

```bash
uv run python generate_ekt_catalog_openapi.py
uv run python generate_ekt_catalog_openapi.py --check
```

OpenAPI-файл описывает **внешний API партнёра**, не маршруты нашего FastAPI. `CatalogProductFacts` присутствует в `components.schemas` как целевой внутренний контракт, но не объявлен ответом партнёра. Структура `offers` не выведена из пустых массивов: в схеме элементы намеренно не ограничены.

## Подтверждённые запросы

| Метод и путь | Результат | Что проверено |
| --- | --- | --- |
| `GET /api/products` | `200`, JSON | Страница 1, 20 товаров; `page=1`, `per_page=20`, `count=20` |
| `GET /api/products?page=2` и `?page=3` | `200`, JSON | По 20 товаров; `page` соответствует запросу |
| `GET /api/products/detail?id=515291` | `200`, JSON | Детальная карточка, общий остаток и 24 склада |
| `GET /api/products/detail?id=<id>` | `200`, JSON | Ещё 12 карточек из первой страницы: остаток 0 или больше, 10 либо 24 склада |
| `GET /api/products` без Basic Auth | `401` | `{"error":"Unauthorized"}` |
| `GET /api/products/detail` без `id` либо с `id=abc` | `400` | `{"error":"Missing product ID"}` |
| `GET /api/products/detail?id=999999999` | `404` | `{"error":"Product not found"}` |
| `GET /api/products?page=0` либо `?page=bad` | `200` | Сервер вернул первую страницу; `page=1` |

Доступ: HTTP Basic Auth по HTTPS. Секреты брать из локального хранилища конфигурации, не из кода, логов или OpenAPI-файла. Проверены только запросы на чтение. `id` в деталях — числовой ID, **не артикул**. Параметр поиска по артикулу не указан в выданном контракте и не подтверждён. Для UC-01 пока нужно найти способ сопоставления артикула и ID: обход страниц либо согласованный с партнёром поисковый endpoint.

## Поля ответа

| Объект | Наблюдаемые поля и типы | Примечание |
| --- | --- | --- |
| Страница | `page: int`, `per_page: int`, `count: int`, `items: list` | В проверенных страницах `count` равен длине `items`; общий объём каталога не указан. |
| Товар в списке | `id: int`, `name: str`, `article: str`, `price: int`, `image: str \| null`, `url: str`, `url_api_detail: str`, `offers: list` | Нет количества, складов, характеристик или сертификата. |
| Детальная карточка | `id: int`, `name: str`, `article: str`, `description: str`, `price: int`, `quantity: int`, `stores: list`, `image: str \| null`, `url: str`, `offers: list`, `properties: object` | `quantity` — общий остаток; в 13 проверенных карточках он равен сумме `stores[].quantity`. Это наблюдение, не обещанная инварианта. |
| Склад | `id: int`, `name: str`, `quantity: int` | Наличие по конкретному складу надо показывать с его названием. |
| Свойства | Переменные ключи; значения `str` или `list[str]` в проверенных карточках | Примеры кодов: `CML2_ARTICLE`, `KATEGORIYA`, `NOMINALNOE_NAPRYAZHENIE`, `NOMINALNYY_TOK`; набор зависит от товара. |
| Ошибка | `error: str` | Форма подтверждена для `400`, `401`, `404`. |

В 60 позициях списка и 13 деталях `offers` был пустым; тип его элементов **неизвестен**. `image` бывает `null`. Единица/валюта `price` не передана отдельным полем и не подтверждена. В ответах нет времени обновления данных. Для `fetched_at` сохранять время собственного запроса и не называть его временем обновления склада.

## Связь с ТЗ

| Требование | Что даёт API | Что остаётся выяснить или сделать |
| --- | --- | --- |
| UC-01: артикул, название, характеристики | `article`, `name`, `description`, переменные `properties` из detail | Сопоставление пользовательского артикула с `id`; какие свойства значимы для разных категорий. |
| UC-01: наличие | `quantity`, `stores[].quantity` из detail | Свежесть данных и правила доступности склада покупателю. Не делать вывод о доступности позиции из одной карточки списка. |
| UC-01: сертификат | Отдельное поле/URL не обнаружены в проверенных карточках | Запросить источник сертификатов; отсутствие поля не равно доказанному отсутствию сертификата. |
| UC-02: аналог | Товарные свойства и остатки можно сравнивать после загрузки detail | Критерии эквивалентности, охват каталога и подтверждение релевантности. `offers` не считать аналогами без контракта. |
| UC-03: оплата, доставка, минимальная партия | Эти поля не представлены в проверенных ответах каталога | Нужен утверждённый источник условий покупки. |
| UC-04: добавление после согласия | Только чтение товаров и остатков | Нужны API корзины, привязка к покупателю и повторная проверка остатка перед действием. |
| UC-05: прямая ссылка на корзину | API каталога не возвращает ссылку на актуальную корзину покупателя | Нужен контракт корзины/оформления и проверка её состояния после UC-04. |

Внутренний `CatalogProductFacts` сохраняет источник, время запроса, артикул, характеристики, цену как **сырое число**, общий остаток и склады. `category` и `certificate_url` допускают `null`: их нельзя заполнять догадкой. Модель описывает целевые данные, но преобразование из API, интеграция чата и корзины ещё не реализованы.
