# Входные документы и реальные результаты обработки

Здесь лежат файлы, которые покупатель может приложить к одному чату: заявка из ERP, письмо снабжения, проектная спецификация, скан накладной, фото товара и текст электрика. Каждый файл проверяет отдельную задачу; это не одна таблица, пересохранённая семь раз.

Основание: [Word ТЗ HackAlem](<../docs/source of truth/assets/HackAlem AI_ ИИ-ассистент для чата на сайте ekt.kz.docx>), разделы 3–7, 8 (обращение к менеджеру), 9. Идеи [TMP_real_out_files.md](../TMP_real_out_files.md) адаптированы к консультации по каталогу и подтверждаемой корзине. Сметы, автоматическое КП, оплата и оформление заказа не добавлены в объём продукта.

**Происхождение:** рабочие формы, номера заявок, объект и требуемые количества смоделированы; это не документы реальных клиентов. Коды товаров взяты из предоставленного каталога. `product_photo.jpg` — неизменённая фотография товара с ekt.kz, её URL указан в manifest; она не выдаётся за съёмку клиента с объекта. Внутри документов нет «учебной спецификации», ответов бота, платёжных или персональных данных.

## Что загрузить

| Файл | Откуда такой вход бывает у покупателя | Что проверяет |
| --- | --- | --- |
| [purchase_request.xlsx](inputs/purchase_request.xlsx) | Выгрузка заявки снабжения из ERP | Два листа; внутренние коды отличаются от артикулов; формула с сохранённым результатом; повтор одного товара. Четыре строки → три товара, всего 6 шт. |
| [procurement_request.docx](inputs/procurement_request.docx) | Письмо отдела снабжения | Товары в абзацах и таблице; количество одной позиции «уточняется». Пожелание по сроку не становится обещанием магазина. |
| [project_specification.pdf](inputs/project_specification.pdf) | Проектная спецификация по щитам и освещению | Две страницы, обозначения QF/EL и три товарные строки. Для отсутствующей позиции нужен объяснённый доступный аналог. |
| [delivery_note_scan.pdf](inputs/delivery_note_scan.pdf) | Скан накладной для повторной закупки | Только растровое изображение страницы, без текстового слоя; две позиции и количества из таблицы. |
| [delivery_note_image.jpg](inputs/delivery_note_image.jpg) | Изображение накладной из мессенджера | JPEG той же накладной: две позиции извлекаются из пикселей, без текстового слоя. |
| [product_photo.jpg](inputs/product_photo.jpg) | Фото маркировки нужного аппарата | Мелкая маркировка неоднозначна: бот просит код/крупное фото. После уточнения покупателем `027005` находит правильный товар; количество — 2 шт. |
| [erp_export.csv](inputs/erp_export.csv) | Машинная выгрузка заявки | UTF-8, разделитель `;`, внутренние коды, комментарий с `;`, цены другого предложения. Цена ekt.kz берётся только из API. |
| [electrician_request.txt](inputs/electrician_request.txt) | Сообщение электрика | Количества словами, разговорный язык, одна позиция без количества — требуется уточнение. |

Excel, Word, PDF и JPEG — входы из ТЗ. CSV/TXT — дополнительные форматы приложения. Не заявляется поддержка всех особенностей 1С или произвольных накладных: Windows-1251, старый DOC, нечитаемая маркировка, единицы «метры/бухты» и дробные количества нуждаются в отдельных проверках и подтверждённом контракте единиц каталога.

## Как попробовать

1. Запустите `make dev` по [README проекта](../README.md#запуск). В чате должен быть режим «ИИ подключён · каталог ekt.kz».
2. Откройте чат → приложите **один** файл из таблицы. Точное сообщение для каждого входа — `prompt` в [manifest.json](manifest.json) и [ожидаемые результаты](expected-results.md).
3. Отправьте сообщение. Во время ожидания виден статус обработки. Сверьте каждую распознанную позицию и количество с оригиналом; отметьте готовые строки. Неизвестное количество не заменяется единицей.
4. «Проверить выбранное» готовит состав. До отдельного «Да, добавить» корзина не меняется. При нехватке остатка и изменении цены вся партия проверяется заново.
5. После согласия откройте актуальную корзину по ссылке. Для ERP-заявки ожидается `027005` — 3, `027028` — 1, `027220` — 2 шт., если доступен такой остаток.
6. Если нужен человек, нажмите «Связаться с менеджером»: проверьте черновик, скопируйте его и откройте опубликованный канал магазина. Обращение автоматически не отправляется; документы и история не передаются.

## Что является доказательством

- [manifest.json](manifest.json): содержимое и SHA-256 каждого входа, коды/ID/количества, соответствующий UC. Это ожидаемая семантика, а не ответы модели.
- [verification.json](verification.json): последний фактический прогон, дата, модель, длительности, извлечённые строки, сравнение фактов с каталогом, согласие и статус каждого случая.
- [observed-session.json](observed-session.json): реальные ответы API для этих файлов и реплик пользователя; токены согласия, cookies и ключи не сохраняются. Продукт не читает этот файл.
- [use-cases.md](use-cases.md): пять обязательных UC и их проверяемые результаты.
- [demo-day.md](demo-day.md): короткий порядок показа рабочей цепочки.

**Фактический результат:** семь файлов дают точные позиции и количества непосредственно после загрузки. Восьмой, `product_photo.jpg`, требует уточнения кода; после него найден правильный товар. Четыре реплики о помощи/заказе проверены отдельно. Поля `direct_match` и `all_files_matched_without_clarification` не позволяют выдать уточнение за успешное чтение фото.

Первоначальный эталон для фото предполагал код по URL карточки. Живые попытки показали разные чтения мелких символов, поэтому это ошибочное предположение зафиксировано как ограничение источника. Само фото сохранено без улучшения; неуспешные попытки остались в `previous_runs`. Критерий теперь проверяет честное уточнение без точного автоматического выбора, затем ответ по явно сообщённому коду.

Старый набор `specification.*` заменён. Старые отчёты доступны в Git; текущие JSON перезаписываются только реальным новым прогоном. Датированные цены и остатки в отчёте не являются обещанием текущего наличия.

## Повторить проверку

```bash
# Из корня. Нужны настроенные серверные доступы; расходует API-бюджет.
backend/.venv/bin/python out/verify_live.py
# или
make test-files-live

# Только локально пересоздать документы и manifest, без вызовов модели:
make examples
```

Генератор использует существующие зависимости и DejaVu Sans (`EXAMPLE_FONT` для другого пути). Оригинальная фотография товара не перерисовывается и не скачивается автоматически: в репозитории сохранены исходные байты с указанным источником. После регенерации отчёт со старыми хешами не подтверждает новые файлы — повторите живой прогон.
